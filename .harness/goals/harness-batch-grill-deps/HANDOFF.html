Why a test, not a benchmark

A benchmark is the wrong instrument here, so I did not build one. The benchmarking loop optimizes a measurable dimension against an exogenous metric - reply rates, cost, latency. It is for problems where you do not know the best answer and must climb toward it. The publish policy is not that: it has one correct answer, it is already known, and the only question is whether every file still agrees. Climbing a hill with a summit already marked is ceremony, not evidence.

The real bug class is policy stated in prose, restated across many files. One changes, the others do not, and nothing catches it because nothing knows they are supposed to agree. That is exactly what happened at the review gate - and then happened again in a fifth file the finding never listed.

So the guard scans; it does not hardcode a file list. It walks every markdown file under skills/ and docs/ plus README.md/CLAUDE.md, keeps the ones mentioning lavish-axi share, and asserts against those. A sixth file drifting is covered the day it is written. A guard that only knows today's files would reproduce today's bug.
